```text
大模型系统输出 -> 用AI优化系统 -> 系统性能提升 -> 更好的大模型输出
```

也就是说，大模型系统既能产生新的大模型输出，又能支撑大模型的基础设施，而我们再用大模型回去优化大模型系统本身。这样一来，系统不仅能够快速服务高性能模型，还能利用模型来进一步提升自己的运行效率，这就是我们所说的良性循环。本节课会从多个角度依次介绍这项工作的背景、核心组件、评测方法和具体应用。


### 一、背景与良性循环

上一节我们简单介绍了FlashIn的总体目标，本节中我们来看看为什么要用AI优化大模型系统，以及推理系统在其中扮演什么角色。

近年来，AI for AI System已经成为一个越来越重要的话题。在大模型AI系统中，最重要的系统其实是大模型的推理系统。当前已经有很多成熟的推理相关系统，例如SGN和VIRM，它们都是由相关校友或团队开发出来的。这些系统已经非常成熟，如果深入观察，你会发现它们的基本结构长得差不多。它们都会调用一系列GPU Kernel。

这里先解释一下什么是GPU Kernel。GPU Kernel就是在GPU上面运行的一个程序，它代表一个特定的计算。例如，如果你有两个矩阵，希望计算这两个矩阵的乘积，就需要在GPU上写一个程序来完成这件事，这个程序就是GPU Kernel。代码形式可以简单表示为：

```python
C = A @ B
```

推理引擎的主要工作就是调用一系列GPU Kernel，最后拼凑出整个模型的计算。模型里面可能包含矩阵乘法，还有Attention算子，以及各种归一化算子，这些算子每一个都对应一个GPU Kernel，而推理引擎则把这些Kernel串联起来。


### 二、为什么手写GPU Kernel很难

上一节我们介绍了推理系统会调用GPU Kernel，本节中我们来看看GPU Kernel的编写为什么是一个老大难问题。

GPU Kernel的写法和普通CPU程序肯定不太一样。它是一个非常特化的系统，使用非常特化的语言。不同的硬件上面，GPU的架构长得不一样，不同的负载，例如不同的计算任务，对应的GPU程序也不一样。所以说GPU Kernel是一个高度特化的程序，写好它、写快它是一个非常困难的问题。

目前的方法通常是让几个专家每天查看GPU Kernel的性能问题，并手动优化。但是硬件种类很多，负载也很多，这就需要大量的专家和大量的时间去优化。这就是为什么编写GPU Kernel被认为是一个经典的难题。同时，这也是一个需要特定领域知识的问题，正好适合用AI来解决。


### 三、用AI写GPU Kernel的动机

上一节我们说明了手写GPU Kernel的困难，本节中我们来看看为什么AI有可能胜任这项工作。

近年来，大家应该注意到AI在编写代码方面取得了非常显著的进展。在各种评测中，AI写代码的能力已经很强，甚至很多同学现在已经不自己写代码，所有的代码都是AI写的。GPU Kernel本质上也是代码，只不过是在GPU平台上执行，可能和普通代码长得不太一样。因此自然会产生一个问题：AI能不能写GPU Kernel代码？

大约一年以前，已经有一些初期工作证明AI可以写出一些Kernel代码，其中一部分是正确的，另一部分则可能越来越快。我们也想做这件事情，即怎么用AI来写GPU代码。不过我们希望更有野心一些，不仅是写代码，还要让AI加速真实世界中的AI部署。也就是说，希望AI能够自己把Kernel写好，同时把它整合到大模型系统里面，让AI自动优化大模型系统。或者，在某些硬件上面无法跑大模型的情况下，我们是否能让AI自动在那个硬件上写一个大模型系统，把模型跑起来。这就是我们的总体目标。


### 四、三个目标与三个组件

为了完成上面的目标，我们把它拆解成了三个部分，并分别设计了三个不同的组件来解决这三个问题。

以下是三个拆解目标：

1. 怎么把Kernel定义好，明确优化的目标是什么。
2. 怎么把各种评测做好，让AI能够生成这些Kernel，并给出正确的反馈，使AI不断写出更好的Kernel。
3. 怎么把AI生成的这些Kernel自动放到应用程序里面，直接用于生产的大模型系统。

对应的，我们设计了三个组件。第一个组件是FlashIn Trace，第二个组件是FlashIn Dataset，第三个组件是FlashIn Apply。下面我们逐一介绍。


### 五、FlashIn Trace：Kernel描述格式

上一节我们介绍了三个组件，本节中我们来看看第一个组件FlashIn Trace具体是做什么的。

FlashIn Trace是一个基于JSON的Schema，用来描述大模型Kernel优化里面的各个部分。它包含四个不同的部分，下面通过代码块展示一个简化的结构：

```json
{
  "definition": {
    "kernel_type": "GEMM",
    "input_shapes": [...],
    "output_shapes": [...],
    "data_types": [...],
    "semantics": "matrix multiplication"
  },
  "solution": {
    "kernel_code": "...",
    "language": "triton"
  },
  "workload": {
    "inputs": [...],
    "source": "real_serving_engine"
  },
  "benchmark_results": {
    "latency_ms": 0.5,
    "throughput": "..."
  }
}
```

第一部分是definition，用来描述这个Kernel有哪些参数，有哪些输入和输出，输入输出的形状是什么样的，数据类型是什么样的。这本身就是对一个Kernel的描述。

第二部分是solution，用来描述已经写好了一个Kernel，并把这个Kernel存储在这里。我们有专门的格式来存储写好的Kernel。

第三部分是workload。工作负载用来描述如果要评测这个Kernel，应该用什么样的输入来判断它对不对、快不快。这些输入是从真实的推理引擎里提取出来的，所以具有一个重要特点，就是真实性，能够反映真实大模型系统里面负载的样子。

第四部分是benchmark_results，用来把所有的输入、输出以及性能数据汇总到一个JSON里面，这就是评估结果。

为什么需要设计这个Schema？有人可能会问，已经有那么多格式了，为什么又设计一个新的，是不是太复杂了？我们认为有非常正当的理由。

第一，对于工程师和大模型推理系统的设计者来说，他们需要一个很清楚的输入输出标准，来描述每个Kernel的输入形状和输出形状，而目前还没有比较好的标准。

第二，对于AI Agent来说，它需要一个非常精确的优化目标。如果目标不精确，Agent就可能做出错误的事情，所以说必须非常精确。

第三，对于很多工具，例如分析工具、优化工具、评测工具来说，它们之间需要一个好的接口来互相交流。这个接口就是我们设计这个格式的原因，让大家都使用同一套接口。


### 六、FlashIn Schema的具体字段

刚才我们介绍了FlashIn Trace的整体结构，本节中我们来深入看看这个Schema里面的具体字段长什么样。

以definition部分为例，它至少包括以下四个方面。

第一个方面是Kernel的类型。常见的Kernel类型包括GEMM，也就是矩阵乘法；GQA，这是一种特殊的注意力Kernel；MRA，也是注意力Kernel；还有归一化Kernel、SoftmaxKernel，甚至包括一些Fieldel Kernel。这就是Kernel的类型。

第二个方面是支持用户指定维度。例如矩阵乘法，通常有一个M乘以N的矩阵，一个N乘以K的矩阵，相乘得到一个M乘以K的结果矩阵。这里的M、N、K就是我们定义的标准形状指标。而且我们支持动态形状。

第三个方面是接口定义。接口包含若干个输入张量和若干个输出张量。每一个输入和输出都可以分别指定形状、数据类型等等。

最后一个方面是语义。语义用来描述这个Kernel到底做了什么计算。知道输入和输出之后，还需要知道输入怎么变成输出。我们会先写一个参考实现，后面Agent的优化就会根据这个实现来进行。


### 七、FlashIn Dataset：数据集构建

讲完了JSON Schema，下面我们来讲一下数据集是怎么收集的。

以下是数据集的收集流程：

1. 先写好Kernel的定义，这部分需要人工来完成，因为我们需要确定哪些算子比较重要。
2. 捕获一些Workload，也就是从大模型系统里面提取典型的负载。
3. 拿到负载之后，就可以对真实的系统进行评测了。
4. 让AI去生成Solution，使用这个负载和Kernel实现来做跑分，也就是Benchmark。
5. 把结果放到评估集里面。

怎么做这个Tracing呢？从一个比较高的视角来看，左边是大模型，右边是真实的请求。我们在大模型系统上面做推理，并且提供一些比较典型的推理配置。在做推理的同时，就能从中获得一些典型的Kernel和负载。最重要的是，我们强调real world relevance，也就是说在真实世界中捕获的负载仍然是非常有现实价值的。


### 八、评测环境与Agent优化循环

有了数据集之后，下一步就是讲评测的过程。

以下是评测环境的主要功能：

1. 给Agent设计一个评测环境。
2. 把Kernel定义输入给语言模型Agent，例如DeepSeek、千问等。
3. Agent根据定义生成一个好的Kernel，并包装到Solution里面，可以是Triton格式、CUDA格式等不同语言。
4. 系统帮助构建Kernel并进行评测，处理依赖、编译、缓存等细节。
5. 支持分布式评测和集中式评测，并且有各种隔离需求。

我们的Kernel Builder是一个相对复杂的系统，里面支持了很多细碎的功能，主要目标是让AI写出的各种Kernel都能成功构建。它支持多种语言，例如Python、Triton，还支持很多第三方库，并且有缓存来加速组件构建。

对于评测系统来说，核心要求是高效，同时还要鲁棒性好，也就是说要比较稳定。为了高效，我们做了分布式评测，每一个设备上都有一个分别的Worker。如果有多张显卡，就可以把很多Kernel分布到不同的卡上面去测试。为了鲁棒性，我们做了隔离，也就是说每一个Solution的评估都需要开一个新的子进程来做，这样不同子进程之间不会有数据污染。

在评测的时候还发现一个具体的问题，就是有一些Kernel不容易确定正确性。例如采样Kernel，输入一个数据分布，输出一个值，要从采样分布里判断这个Kernel对不对，这很麻烦。我们的做法是不只做一次采样，而是做多次采样，例如1万次或10万次，形成一个采样分布。如果一个Kernel是正确的，我们希望这个采样分布和原始输入分布是一致的。也就是说，我们做大量采样，然后判断这两个分布之间的距离。如果距离比较小，就可以认为这个Kernel的实现没有大问题。

有了这些基础设施之后，我们就能实现一个Agent。在系统图中，标有Logo的部分是已经有的部分，Agent负责调用这些部分来实现自己优化Kernel的循环。也就是说，一个Kernel先输入定义和Workload，然后优化得到一个Solution，之后连接到Benchmark里面，去看性能好不好、够不够正确。如果够好了，就输出出来；如果还不够好，就交给另一个Agent去判断是否有Bug、是否有问题，然后反过来再提供反馈，进一步改进。这就是我们的系统概貌。


### 九、FlashIn Apply：生产环境部署

刚才我们讲了怎么评测一个Kernel，这是评测部分。本节中我们来看看第三步，已经有了一个好的Kernel，怎么能把它用到我们的服务引擎、大模型系统里面。

我们的方法叫做FlashIn Apply，这是一个我们开发的实用工具。我们希望把好的Kernel选出来，并且用到比较复杂的大模型系统里面。

怎么做呢？如果你深入观察大模型系统，会发现大部分大模型系统都依赖于一个第三方库，叫做FlashIn。FlashIn是一个算子库，包含了大模型推理时用到的算子。虽然大模型很复杂，但是它调用算子库是相对简单的。我们做的一件事情是直接劫持大模型对于算子库的调用，然后替换成我们自己的Kernel，本质上就是这么一件事情。

深入看我们自己的办法。先找到FlashIn的接口，就能知道现在要调用什么样的Kernel，这个Kernel的速度、接口、输入是什么。然后被我们的FlashIn Apply函数拦截。拦截之后，就被替换成跑得最快的那个Kernel，指的是我们AI生成的、跑得最快的可能。

并且我们希望这是一个不需要代码的方式。什么叫不需要代码的方式？只要导入这个库，并且设置某一个特定的环境变量，这个Kernel就会自动被替换成最好的这个Kernel。


### 十、如何选择最优Kernel

上一节介绍了如何拦截和替换Kernel，本节中我们来看看怎么从数据集里选出最好的Kernel。

以下是选择逻辑：

1. 劫持FlashIn的调用，此时知道输入是什么。
2. 回到数据集，数据集里面已经有很多Kernel，并且每个Kernel都有对应的评测时间。
3. 希望根据评测结果找到跑得最快的Kernel。

具体操作是这样的。第一步，用输入去提取对应的Workload，也就是负载。例如输入里面的批次大小是64，就去负载里面找有没有批次大小等于64的负载。拿到这个东西之后，就可以看所有在这个负载上面的评估结果。假设有10个Kernel都实现了同一个功能，在这64的负载上面，它们应该有不同的速度。这时候就提取它们的速度。

拿到速度之后，就能选出跑得最快的Kernel在哪里。然后再去查Solution，找到跑得最快的Kernel实现在什么地方。最后，把这个最好的Solution和输入运行起来，把输入送给它，返回结果。这个结果就变成了真实输出。

所以说，相当于原来调用了FlashIn的某个Kernel，现在我们不调用它了，调用从数据集里生成的AI Kernel，但是仍然返回一样的结果。因为这个Kernel实现更快，就可以加速推理。


### 十一、Workload捕获的其他功能

除了替换Kernel，FlashIn Apply还有其他功能。

例如刚才说的从大模型系统里提取Workload，这也是利用这个功能来实现的。怎么做呢？每次先劫持FlashIn Kernel的调用，在不替换Kernel的情况下，直接把输入存储到磁盘上的某个位置，并且整理到磁盘上。这样的话，同样的工具还可以用来Trace Workload，这也非常有帮助。


### 十二、应用：排行榜、标准化文档与比赛

介绍完了技术难点，下面我们来讲具体的应用。

第一个应用是构建一个Leaderboard，也就是排行榜，基于FlashIn Dataset来做。现在有很多不同的模型和Agent，我们想利用这些Agent，排序哪个Agent跑得快，哪个Agent跑得慢，哪个效果更好，所以需要一个排序。

排序的结果可以用下面的图来理解。首先定义了一个指标，叫做WinRate，也就是和真实的最好的人类模型性能的比例：

```text
WinRate = AI Kernel性能 / 人类最佳Kernel性能
```

看这个曲线，纵轴越向上，意味着比人快的部分越多，比例越高；横轴越向右，意味着加速比越高。纵轴代表的是分布，比如说有80%的Kernel，至少有0.8的加速比。横轴就是这个加速比。曲线的面积越大，就意味着这个Kernel写得越好，反过来也意味着这个Agent写Kernel的能力越强。

除此之外，我们还给每一个常见的Kernel构建了一个标准化的文档，大家可以基于这个文档来优化。这是第一个应用。

第二个应用是基于我们的库，设计了一个新的比赛，叫做FlashIn Kernel Generation比赛。比赛的事情就是让参赛选手来帮我们写Kernel，我们再作为裁判评价他们的Kernel好坏。

比赛的挑战是在最新的硬件B200上面评估Kernel，选择了三个比较难的任务：

1. 融合Kernel，也就是融合的MOE Kernel。
2. 稀疏注意力Kernel，新的模型架构里面会用到的Kernel。
3. Gated DeltaNet，也是一种特殊的注意力Kernel，来自新的模型架构。

我们会在FlashIn Bench上面评估Kernel的快慢，并且把FlashIn，也就是人类专家系统的Kernel作为备赛来比较。

比赛里设置了两条不同的路线：

1. 不能用人工干预，必须用纯Agent来设计。
2. 让专家先来优化这个Kernel，然后人类和专家可以合作一起来优化。

这是两个不同的方向，一个是人和AI一起，一个是纯AI。为了支持这个比赛，我们也做了一些系统上面的改进。例如设计了一个新的东西，叫做远程评测服务器。这个服务器可以让大家远程提交任务，然后评测快慢。为了实现这个功能，基本上实现了一个HTTP服务器，并且可以对所有进来的请求做适当的调度和隔离，这样能让它们运行得又快，又非常安全。

我们还专门为这个东西设计了一些新的API，只要根据这个API，就可以远程把评测Kernel的性能汇报上来。还提供了很多Kernel的基础设施工具，这些工具用来帮助Agent实现不同的Kernel功能。

并且我们和Model合作，提供了远程的云端Kernel执行。很多参赛者可能没有GPU，Model是一个云提供商，有很多GPU，把GPU权限开放给所有参赛选手，这样参赛选手就可以利用它的GPU来在最新硬件上面做Kernel性能优化。

一共是三个track，一共是5个Kernel，因为Track B和Track C分别有两个Kernel。我们也是花了一些精力，从真实的大模型系统里面，把需要比赛的三个不同任务，收集了很多重要的Kernel定义和负载进来。

最后可以看一下收集的结果，比如说每一个Kernel上，都有一个不同的输入分布，包括DSA、GD等等，每一个都有不同的输入。这意味着如果你想提交到正确的Kernel上，它必须在不同的输入上面都有比较高的加速比，这样的话你才能在比赛中胜出。


### 十三、总结

本节课中我们一起学习了如何用AI优化大模型系统。首先介绍了FlashIn的良性循环思想，即利用大模型输出来优化系统自身，再用系统来支持更好的大模型输出。接着解释了GPU Kernel是什么，以及为什么手写GPU Kernel很难。随后说明了AI写代码能力的提升使得AI编写GPU Kernel成为可能，并提出了让AI加速真实世界AI部署的目标。

接着拆解了三个目标，并介绍了对应的三个组件：FlashIn Trace用来定义Kernel，FlashIn Dataset用来收集评测数据，FlashIn Apply用来将生成的Kernel部署到生产系统。详细说明了JSON Schema的设计原因和具体字段，包括定义、Solution、Workload和Benchmark结果。接着介绍了评测环境的分布式评测、隔离机制以及采样判断正确性的方法，并描述了Agent优化Kernel的循环过程。

随后讲解了如何拦截FlashIn调用并替换为最快Kernel，以及如何根据输入匹配Workload从数据集中选出最优Kernel。最后介绍了Leaderboard、标准化文档和Kernel生成比赛等应用，包括比赛的两个轨道、三个任务以及云端GPU支持。
